### 1.1 原始需求复述

用户试玩 4 局，**没有一局能清空金字塔**，提出 3 点：

1. 应尽可能优先组合金字塔上的牌，明牌区内部能配对的也不组合，这样清空金字塔的概率更大；
2. 大量游戏说明占据页面大部分空间，显得不整洁、要读的东西太多、页面复杂；
3. 占卜类型占用空间更大，希望「进来就是金字塔游戏页，其他用弹窗交互」。

### 1.2 主理人已确认的两项决策（本轮方向，不再改动）

| 编号 | 决策 | 落地 |
| --- | --- | --- |
| D1 | 智能提示 + 可解发牌 | 新增「提示」能力，按「优先金字塔牌」策略推荐下一步（明牌区内部组合不优先）；新开局用求解器保证这副牌**确实存在清空金字塔的走法**，不再纯随机洗牌 |
| D2 | 首屏直入游戏 + 全部弹窗化 | 打开页面直接是金字塔棋盘，用默认话题开好一局；话题 / 占卜类型 / 写下内容 / 规则 / 趣味词典 / 免责声明全部收进顶部小按钮触发的弹窗，不再常驻占版面 |

## 2. 产品定义

### 2.1 Product Goals（3 个正交目标）

| # | 目标 |
| --- | --- |
| G1 | **让「清空金字塔」从靠运气变成可达**：可解发牌保证有解，金字塔优先提示保证玩家能顺着解走下去。 |
| G2 | **首屏零负担**：打开即游戏，去掉开局表单与常驻说明造成的信息过载。 |
| G3 | **信息按需可达且不丢失**：所有说明改为弹窗 / 结果弹窗承载，内容保留、位置收敛。 |

### 2.2 本次成功标准（可量化、可验收）

#### 2.2.1 先明确两个概念的关系（必须对齐，避免验收歧义）

| 概念 | 定义 | 判定 |
| --- | --- | --- |
| **清空金字塔**（用户核心诉求 / 本轮主指标） | 金字塔 7 层 28 张牌全部 `removed` | 统计 `pyramid` 区未消除张数 = 0 |
| **52 张全消通关**（既有终极胜利条件） | 52 张全部消除 | `remainingCount = 0`、`evaluate() = 'cleared'` |
| 两者关系 | **52 张全消 ⇒ 金字塔必已清空；金字塔清空 ⇏ 通关**（塔清空后明牌区仍可能无解 → `stuck`） | 金字塔清空是通关的**必要非充分条件** |

结论：本轮把「**金字塔 28 张清空**」设为主验收指标；「52 张全消」作为关联观察指标，不因塔清空但明牌区卡死而误判失败。是否把求解器目标直接提升到「全消可解」见第 6 节 Q1 默认建议。

#### 2.2.2 验收指标表

| # | 指标 | 定义 | 验收标准 | 级别 |
| --- | --- | --- | --- | --- |
| S1 | 发牌可解率 | 求解器验证「存在清空金字塔 28 张的合法走法」的牌局占比 | 批量 ≥ 1000 副牌 = **100%**（QA 自动化） | P0 硬门槛 |
| S2 | 金字塔清空率（跟提示走） | 全程**仅按提示**操作，最终金字塔清空的局占比 | 连续 20 局 = **20/20（100%）** | P0 主指标 |
| S3 | 提示不破坏解 | 从可解牌局出发按提示走，出现「仍有解却提前 `stuck`」的次数 | **0 次** | P0 硬门槛 |
| S4 | 完整通关率 | `cleared` 局占比 | 记录 20 局 `cleared` 数作为观察值；若采纳 Q1 全消目标则须 **20/20** | 关联指标 |
| S5 | 首屏负担 | 打开页面到可点第一张牌的点击次数 / 首屏常驻说明字数 | **0 次点击**；常驻说明文字 ≈ 0（HUD 数值标签除外） | P0 |
| S6 | 改版前基线 | 用户实测 4 局，金字塔清空 **0 次** | 作为对比基线写入 QA 报告 | 参照 |

### 2.3 User Stories

| # | 用户故事 |
| --- | --- |
| U1 | As a 休闲玩家，I want 打开页面直接看到金字塔棋盘并开始消牌，so that 不用先读一大段表单和说明。 |
| U2 | As a 连续几局没清空金字塔的玩家，I want 点「提示」后优先指给我该消哪两张**金字塔牌**，so that 我能更快拆塔，而不是把机会浪费在明牌区内部配对上。 |
| U3 | As a 玩家，I want 每一副新牌都保证存在清空金字塔的走法，so that 不会一开局就注定白玩。 |
| U4 | As a 想了解规则 / 换话题的玩家，I want 规则与话题设置收进顶部小按钮，so that 想看时点开、不看时不占屏幕。 |
| U5 | As a 关心趣味解答与免责的玩家，I want 这些说明仍可查（弹窗或结果弹窗里），so that 内容不丢失、只是不再常驻。 |

### 3.2 「提示」产品定义 —— 优先级顺序（严格递减）

| 档 | 组合 | 说明 |
| --- | --- | --- |
| 1 | **金字塔牌 + 金字塔牌** | 两张均已完全露出、和为 13 |
| 2 | **金字塔牌 + 明牌牌** | 露出金字塔牌与已翻明牌、和为 13 |
| 3 | **金字塔 K 单消** | 已完全露出的金字塔 K 单点消除 |
| 4 | 明牌牌 + 明牌牌 | 明牌区内部配对，和为 13（**不优先推荐**） |
| 5 | 明牌 K 单消 | 已翻明牌中的 K 单点消除 |
| 6 | **翻一张手牌**（默认补充） | 1~5 档均无可用组合且 `stock` 未空时，提示点击手牌堆翻牌 |

要点：

1. 只要 1~3 档存在可用走法，**不得**推荐 4~5 档（对应用户「明牌区有组合的也不组合」）。
2. 同档内多条候选时，必须按 **P0-3「不破坏可解路径」** 过滤后再取，具体算法交架构师。
3. 第 6 档是为避免「有牌可翻却报无提示」的死锁；翻牌后重新计算提示。
4. K 单消与「被压住的 K 不可消」既有顺序不变（见第 5 节不改清单）。

### 3.3 「提示」交互形态（按钮 / 高亮 / 文案）

| 形态 | 定义 |
| --- | --- |
| 按钮 | HUD 常驻「提示」按钮；动画 / `busy` 期去抖，不重复触发；**不限次、无冷却**（Q5 默认） |
| 高亮 | 推荐的一对（或单张 K）在金字塔 / 明牌区**跨区同时高亮**（描边 + 呼吸）；第 6 档则高亮手牌堆按钮；一次有效操作后或短时自动清除 |
| 文案 | 按钮附近或棋盘上方一行短句，随档位变化，例：<br>档 1/2「先消金字塔上的这两张」；档 3「金字塔上的 K 可以直接点掉」；档 4/5「金字塔暂时配不上，先消明牌这两张」；档 6「金字塔暂时配不上，先翻一张手牌」 |
| 执行 | 默认**只高亮 + 文案，不自动替玩家消除**（Q6 默认） |

### 3.4 无可用提示时的反馈

| 场景 | 反馈 |
| --- | --- |
| 1~5 档无组合，但 `stock` 未空 | 给第 6 档「翻一张手牌」提示，不报「无提示」 |
| 1~5 档无组合，且 `stock` 已空 | 文案「这局没有可消的组合了」，按既有 `evaluate()` 判 `stuck` 并弹结果弹窗 |
| 仍有合法走法 | **不得**返回「无提示」（由 S3 覆盖） |
